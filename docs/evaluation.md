# Evaluation

This is what running `eval/` against this repo's own content actually found, not a projection of what it should find. See `eval/README.md` for how to reproduce it.

## Setup

22 hand-written question/answer pairs (`eval/qa_pairs.jsonl`) against this repository ingested as its own corpus: 95 files, 289 chunks after AST-aware chunking. Categories: exact identifier lookup, semantic/paraphrase, cross-file, code-specific, and two unanswerable questions used to check the system doesn't confidently return irrelevant files.

Ground truth is the expected source file(s) per question, not exact line ranges, since AST chunking boundaries can shift slightly without changing which file holds the answer.

## Retrieval strategy comparison

Generated by `eval/ablation.py` against this repo (2 CPUs allocated to `retrieval-service`, embedding on CPU):

| Strategy | Recall@5 | MRR | Avg latency | Avg context tokens |
|---|---|---|---|---|
| Dense only (Qdrant) | 0.70 | 0.51 | 1056 ms | 2155 |
| Lexical only (bm25s) | 0.55 | 0.40 | 32 ms | 2504 |
| Hybrid (dense + lexical, fused) | 0.70 | 0.45 | 760 ms | 2442 |
| Hybrid + reranker | 0.80 | 0.49 | 26018 ms | 2010 |

**Finding 1: plain hybrid fusion did not beat dense-only.** Recall@5 tied at 0.70, and hybrid's MRR (0.45) was lower than dense-only's (0.51). Lexical-only alone is the weakest of the four by both metrics. Dense embeddings alone already retrieve the right file for 70% of these questions, and fusing in BM25 results at the query classifier's current weights sometimes displaces a correctly-ranked dense hit rather than reinforcing it. The fusion weighting in `query_classifier.py` would be the first thing to tune if this needs to improve; as shipped, plain hybrid fusion is not earning its complexity on this corpus.

**Finding 2: reranking does improve recall, at a steep cost.** Hybrid + reranker reached 0.80 recall, the best of the four, a real +0.10 over dense-only. But average latency went from about 1 second to 26 seconds per query: a roughly 25x increase, from a cross-encoder (`ms-marco-MiniLM-L-6-v2`) running on CPU over the fused candidate pool. On this hardware that cost is not worth a 0.10 recall gain for an interactive chat or agent response. It might be worth it for an offline or batch use case, or on a GPU where the same model runs far faster. `reranker.py` stays off by default; the ablation is what should decide whether to turn it on for a given deployment, not an assumption either way.

**Default recommendation from this data: dense-only retrieval.** It ties hybrid on recall, beats it on MRR, and is meaningfully faster (1056ms vs 760ms is close, but both are far cheaper than reranking, and dense-only avoids maintaining and querying the BM25 index at all for a result that isn't measurably better here). The code keeps hybrid available and configurable, not removed, since a different corpus (larger, more identifier-dense) could tip this result the other way; that is exactly what re-running this ablation against a new corpus is for.

## Unanswerable questions

`unanswerable_clean_rate` was 0.0 across strategies: the two unanswerable test questions still returned some chunks rather than confidently returning nothing. This is an accurate reflection of how the system currently works. `Search` always returns up to `top_k` results with no relevance-score cutoff, so a question with no real answer in the corpus still gets back "closest available" chunks. A relevance threshold (dropping chunks below some fusion-score cutoff) would improve this, at the cost of sometimes dropping a real but weakly-scored match. Not implemented here; noted as a real, measured gap rather than an assumed one.

## Reproducing this

```bash
make up
make pull-model
make ingest-self
make eval
```

`make eval` runs `run_eval.py` once against the default hybrid strategy, then `ablation.py`, which regenerates the table above and overwrites `eval/report.md`. The reranked pass is slow (see above); a full ablation run on modest hardware takes several minutes, most of it in that one pass.

## What this does and doesn't claim

This is a 22-question benchmark on a roughly 95-file corpus. It is not a claim of statistical significance, and the specific Recall@K/MRR numbers above will shift with corpus size, embedding model choice, and the exact question set. What it does demonstrate is a working, reusable measurement pipeline: point it at any ingested corpus and it produces the same comparison, honestly, rather than assuming which retrieval strategy is better.
